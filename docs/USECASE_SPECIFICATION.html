3. Overview

An AI agent can complete a task while skipping approval, choosing the wrong tool, repeating retrievals, or relying on unsupported evidence. Evaluating only the final answer can miss these execution failures.

AgentProof is an agent observability platform. It collects execution traces from evaluation runs and from production, checks tool use and policies, compares actual actions with expected workflows, and links confirmed findings to inspectable evidence. Developers investigate individual runs and sessions; reviewers assess findings; evaluation engineers and CI systems compare versions before a release; operators watch behavior, usage, and cost in production.

The behavioral layer is what sets it apart. The same deterministic, completeness-aware detectors run on CI evaluations, where they gate releases, and on sampled production traffic, where they surface drift. Model-assisted judgments help, but they never become facts without validated evidence. Outcome success and behavioral correctness remain separate. The initial reference domain is customer support: a successful refund can still violate an approval requirement. Other domains need their own tool specifications, policies, and evaluation data.

Positioning statementFor teams building and operating AI agents, AgentProof is an agent observability platform whose behavioral findings are verified against trace evidence and versioned policies. Most observability tools score traces with LLM judges whose citations are never checked. AgentProof evaluates conditional and ordered policies deterministically, refuses to call a run clean when the trace is incomplete, and uses one rule set both to gate releases and to monitor production.

Differentiators to defend:

  • (1) Evidence-validated findings (BR-01, UC-08).
  • (2) Versioned policy-as-code with conditional and ordering rules, evaluated deterministically and linked to findings and gates (UC-06).
  • (3) Completeness-aware reasoning with explicit INCONCLUSIVE and fail-closed ERROR (BR-02, BR-06).
  • (4) One rule set across CI gating and production monitoring (UC-12, UC-14).

Not differentiators: trace capture, dashboards, datasets, and LLM judges are expected by users of any observability product. Separating outcome from behavior (BR-05) is established practice since τ-bench; AgentProof keeps it as a rule, not as a selling point.

Market risk: the observability segment is consolidating into large data and security vendors. A full platform competes on breadth with well-funded incumbents. The differentiators above must therefore be visible in the first slice and must not depend on breadth.

5. Out of scope

Hosting or executing arbitrary customer agent codeCustomer CI executes cases in its own environment. AgentProof evaluates the resulting traces.
Replacing a CI serviceAgentProof supplies a gate decision and a thin client (FR-16) that existing CI pipelines call. Agent telemetry storage is in scope as of version 0.2. AgentProof's own operational telemetry still goes to a separate operational backend.
In-path runtime enforcementAgentProof does not sit between the agent and its tools or block calls live. Enforcement products such as Cedar-based gateways cover that. AgentProof evaluates the resulting traces and reports gaps.
Simulating end users or generating test conversationsCases and any user simulation run in the customer's environment (for example, τ-bench-style simulators). AgentProof consumes the traces.
Alerting and notification routingDeferred beyond Phase 2. Production findings and metrics are visible in the UI and API first.
Prompt management and playgroundsPrompt and code revisions are recorded as agent-version metadata; editing and serving prompts is not provided.
Eliminating human review of ambiguous findingsInsufficient evidence remains explicit; reviewers can annotate findings.
Automatically rewriting prompts or agent codeThe initial product reports and recommends; it does not repair agent implementations.
Formal proof of unrestricted natural-language behaviorSemantic judgments remain evidence-dependent and carry uncertainty.
Fine-tuning LLMsNot part of this design.
Retroactively stopping an already executed tool actionAnalysis reports the observed action and risk; it cannot undo execution.
Production guaranteesService levels and operating procedures are proposals, not verified capabilities. The CI client (FR-16) is a first-slice requirement, not a released product.

IDDecisionChosen optionAlternatives considered and trade-offs
D1Product positioningFull agent observability platform with the evidence-validated behavioral layer as its differentiator; production scope covers online evaluation, sessions, and usage dashboards (Requester). Trade-off: a crowded, consolidating market and a large scope.
  • Evidence-backed release gate that complements existing observability tools: narrower scope and a clear buyer, but depends on customers running cases in CI.
  • Runtime enforcement: sits in the request path (latency, availability) and competes directly with AWS and Snyk.
  • Audit-evidence angle (EU AI Act Articles 12 and 14; high-risk obligations deferred to 2 December 2027): useful later, but risks being read as a compliance claim.
D2Policy and workflow specification formatVersioned JSON predicate schema, formalizing what 02_seed.sql already uses ({"tool","arg","op","value"} conditions, prior_steps, ordered and forbidden transitions) (Default). Deterministic, easy to validate. It cannot express repetition counts or data flow between steps.
  • Temporal-logic DSL in the style of AgentLTL: more expressive, but harder to author and costlier to implement.
  • Cedar: interoperates with AgentCore, but Cedar authorizes individual requests, so ordering rules need custom extensions.
  • Optional add-on for any format: an LLM drafts rules from natural-language policy text, and a person approves them before publication.
D3Agent nondeterminismk trials per case, reporting pass^k and per-case consistency. For a mandatory policy, a violation in any trial means FAIL (Requester). CI cost grows by a factor of k.
  • One trial per case with cross-case statistics: cheaper, but hides flaky cases.
  • No treatment: the gate can flip between runs.

  • Gate-blocking critics on a frontier API model: costly, sends data off-site, and makes the gate nondeterministic.
  • No critics or RCA in the first slice: simplest, but loses UC-08.

Status: DraftPriority: Must within stated scopeScope: FoundationRequirements: FR-01, NFR-04, NFR-07, NFR-09

Description

Give a person or machine only the project resources and operations it is entitled to use.

Actors

Human user, CI client, collector. Supporting actor: Project administrator.

Preconditions

A project exists; the identity is registered and mapped to that project. A human can complete OIDC sign-in; a machine can obtain a client-credentials token.

Trigger

An actor requests a protected API operation.

Postconditions

  • On success: No cross-project resource data is disclosed; an authorized operation may proceed.
  • On failure: The protected operation is denied; no cross-project data is disclosed.

Main flow

  1. Auth0 issues an access token for the intended API audience with appropriate scopes.
  2. Traefik Proxy routes the request to the backend and applies rate and body limits.
  3. FastAPI validates the token’s signature, issuer, audience, and expiry, resolves the actor and project context, and checks operation-specific authorization.

A request for a trace in another project is denied even if the token includes traces:read. Disposition: Reject invalid or expired tokens and deny insufficient scope or project access. Missing identity infrastructure ends protected access without granting new permissions.

Acceptance criteria — AC-01

UC-02 — Register an agent and versioned evaluation context

Description

Define the agent, tools, policies, and expected workflows needed to interpret its runs.

Actors

Project administrator and policy owner.

Preconditions

The actors have project administration or policy-writing permissions.

Trigger

The team onboards an agent or publishes a change to its behavior contract.

Postconditions

  • On success: New evaluations can pin exact agent, policy, workflow, and tool-specification versions; historical runs keep their original versions.
  • On failure: Invalid context is not published. Existing versions remain unchanged; projection failures remain visible.

Main flow

  1. The administrator creates an agent identity and registers an agent version, including code or prompt revision metadata where available.

Disposition: Import and validation errors return to steps 2–4 for correction. Publishing a replacement creates a new version. A failed embedding update leaves the authoritative version intact and dependent analysis unavailable until recovery.

UC-03 — Ingest and normalize an agent trace

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-03, NFR-01, NFR-04, NFR-05, NFR-07

Description

Turn an agent's telemetry into a project-scoped canonical execution record without performing expensive analysis in the request path.

Actors

Customer agent or OTel Collector.

Preconditions

The caller has a scoped ingestion identity and an existing project and agent version. A redaction configuration is active.

Trigger

The caller submits OTLP spans that follow the pinned OpenTelemetry GenAI semantic conventions and the AgentProof profile: agentproof.* attributes for project, agent version, case ID and trial number, approval events, and trace completion.

Postconditions

  • On success: An accepted trace is retrievable with a visible processing state and durable path to analysis.
  • On failure: Rejected input is not acknowledged as accepted. Persisted work remains recoverable and is not reported as analyzed.

Main flow

  1. The gateway and ingestion entrypoint authenticate the caller, enforce project boundaries and payload limits, and validate trace identifiers and structure.
  2. Redaction runs before sensitive fields are persisted. The adapter maps spans to canonical agent, LLM, tool, retrieval, handoff, guardrail, and approval types, using the semconv operation names (for example invoke_agent and execute_tool) and the profile’s approval attributes. The semconv version is recorded on the trace.
  3. The normalizer reconstructs parent-child and chronological relationships and records warnings. It marks the trace COMPLETE only when the root span has ended and carries agentproof.trace.complete=true, or the owning evaluation has been finalized. A trace known to be missing spans is PARTIAL; anything else stays OPEN. Silence is never treated as completion.
  4. The span store writes spans idempotently by project, trace, and span ID. That store is PostgreSQL in the first slice and ClickHouse from Phase 2. PostgreSQL stores the trace record, source metadata needed for diagnostics, and a durable analysis-job record with a stable idempotency key, in one transaction. Acceptance requires both writes.
  5. The ingestion API acknowledges acceptance. Job publication to Redis is retried or recovered by an outbox/sweep if the queue is temporarily unavailable.

Alternative flows and exceptions

UC-03-A1 — Cancellation or interruption

Before submission, the sender may abandon the upload. After durable acceptance, disconnecting does not cancel analysis; a retry uses the same idempotency key.

UC-03-E1 — Exceptions and recovery

Branch: Steps 1–5 of the main flow, as applicable.

Duplicate delivery returns the existing trace or an idempotent acknowledgement without duplicate findings. Malformed payloads, or spans that do not follow the pinned profile, are rejected with actionable errors. A missing parent span is recorded as incomplete structure. A failure in either store prevents successful acceptance. Spans already written are deduplicated when the sender retries. A persisted but temporarily unqueued trace remains recoverable and is never reported as fully analyzed.

Disposition: Reject invalid payloads or unsuccessful persistence without acceptance. Duplicate submissions return the existing result. Incomplete structure remains explicit; accepted but unqueued work stays recoverable and pending analysis.

Acceptance criteria — AC-03

Replaying the same delivery multiplies neither traces nor spans. A worker crash or queue outage cannot silently lose accepted work. Redacted values are absent from normal persisted views. Trace completeness and its reason are available to downstream detectors. A trace without the completion signal never becomes COMPLETE.

Preconditions

Data is associated with a project and has a declared classification, retention policy, and redaction settings.

Trigger

A privileged read, scheduled retention expiry, or authorized deletion request occurs.

Postconditions

  • On success: The system reaches a verifiable deletion state, or explicitly exposes incomplete propagation for follow-up.
  • On failure: Incomplete deletion propagation remains pending and visible; erased source content cannot be restored by a rebuild.

Main flow

  1. The system enforces project and role checks before disclosing trace fields and records privileged raw-payload access.
  2. At expiry or authorized erasure, PostgreSQL marks the source records and manages deletion according to the chosen policy.
  3. A durable deletion job removes or invalidates the matching ClickHouse span rows, pgvector embeddings, evidence snapshots, and any relevant caches. TTL expiry in ClickHouse covers routine retention; this job covers erasure before expiry.
  4. The system verifies the projection state and keeps an audit record that does not itself re-expose erased content.

Alternative flows and exceptions

UC-13-A1 — Cancellation or interruption

Before an authorized deletion request is submitted, the administrator may abandon it. Once deletion starts, closing the interface does not reverse erasure or cancel propagation.

UC-13-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A span-store or embedding outage leaves the request pending with a retryable status and blocks reindexing of deleted source material. A legal or operational hold, if implemented, must be a separately authorized and documented rule. A request for data outside the administrator's project is denied.

Disposition: Deny cross-project requests. A store outage leaves deletion pending and retryable while preventing deleted-source reindexing. Any hold requires a separately authorized, documented policy.

Acceptance criteria — AC-13

Erased data does not reappear after index rebuilds or from evidence snapshots; access to raw payloads is recorded; error paths do not leak sensitive fields; each project can identify its configured retention and redaction policy.

Notes

Shared rules: BR-03, BR-06, BR-11. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-14 — Evaluate sampled production traces online

Status: DraftPriority: Must, Phase 2Scope: Phase 2Requirements: FR-17, NFR-04, NFR-05, NFR-10, NFR-11

Description

Apply the same deterministic detectors used for release gating to production traffic, so policy violations and loops that escape evaluation datasets become visible.

Actors

Analysis worker. Beneficiaries: Agent operator, policy owner.

Preconditions

The production agent exports traces under UC-03 with a deployed agent version that has a pinned evaluation context. A sampling rate is configured for the project.

Trigger

A production trace selected by the sampler reaches a terminal completeness state.

Postconditions

  • On success: Findings and per-version finding rates with denominators (sampled, analyzed, inconclusive) are recorded.
  • On failure: Unanalyzed sampled traces are counted as such; rates are never computed over an unstated denominator.

Main flow

  1. The sampler selects traces deterministically from the trace ID and the configured rate, so the decision is reproducible. The rate is recorded with each decision.
  2. The worker runs UC-05, UC-06, and UC-07 deterministic checks against the policy and tool versions pinned to the deployed agent version.
  3. Confirmed findings snapshot their evidence (BR-11); semantic critics may add advisory findings.
  4. The system aggregates finding rates by agent version and time window and shows them beside the evaluation results for the same version.

Alternative flows and exceptions

UC-14-A1 — Cancellation or interruption

The operator may lower the sampling rate or pause sampling; traces already sampled continue through analysis. Pausing is recorded so the gap is visible in rates.

UC-14-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A trace with no pinned context for its agent version is counted as not analyzable rather than checked against the latest policy. Traces that stay OPEN past the profile timeout are counted as inconclusive. Worker backlog delays results but does not drop sampled traces.

Disposition: Unpinned versions and open traces are excluded with explicit counts; backlog is visible as pending analysis.

Acceptance criteria — AC-14

The refund violation from the reference scenario is detected in a production trace with the same clause and evidence as in evaluation. Every rate shows its numerator, denominator, sampling rate, and exclusions. A production finding never changes a release gate.

Notes

Shared rules: BR-01, BR-02, BR-04, BR-06, BR-09, BR-11. Sampling rates and retention are open in section 7.3.

UC-15 — Inspect a multi-turn session

Status: DraftPriority: Must, Phase 2Scope: Phase 2Requirements: FR-18, NFR-03, NFR-04, NFR-07

Description

Group the traces of one conversation so a developer can follow the agent across turns and policies can depend on earlier turns, such as an approval granted in a previous turn.

Actors

Agent developer, agent operator. Supporting actor: Analysis worker.

Preconditions

Traces carry a session identifier (the semconv conversation ID or the profile’s session attribute).

Trigger

The user opens a session, or a session-scoped policy needs evaluation.

Postconditions

  • On success: The session timeline lists turns in order with per-turn outcome, behavior, and findings; session-scoped checks are recorded.
  • On failure: Missing turns are shown as gaps; session-scoped checks touching a gap are inconclusive.

Main flow

  1. The system orders the session’s traces and shows each turn with its outcome, behavioral state, and findings.
  2. The worker evaluates session-scoped policy clauses over the ordered turns, so a required prior step may appear in an earlier turn.
  3. The user opens any turn in the trace view (UC-04).

Alternative flows and exceptions

UC-15-A1 — Cancellation or interruption

The user may leave the session view at any time; nothing changes.

UC-15-E1 — Exceptions and recovery

Branch: Steps 1–2 of the main flow, as applicable.

A session whose earlier turns are missing, unsampled, or expired cannot support an absence claim that depends on those turns (BR-02). A session spanning agent versions shows the version per turn.

Disposition: Gaps make dependent checks inconclusive; per-turn versions remain visible.

Acceptance criteria — AC-15

An approval in turn 1 satisfies a refund prerequisite in turn 2 when the policy is session-scoped. A missing turn 1 yields inconclusive, not a violation. Turn order and versions are preserved.

Notes

Shared rules: BR-02, BR-03, BR-04. Sampling must keep or drop whole sessions for session-scoped checks to be meaningful.

UC-16 — Monitor usage, cost, and latency

Status: DraftPriority: Must, Phase 2Scope: Phase 2Requirements: FR-19, NFR-04, NFR-11

Description

Show how much an agent consumes and how fast it responds, by version, model, and tool, alongside its behavioral results.

Actors

Agent operator, evaluation engineer.

Preconditions

Spans carry token counts, model identifiers, and timings where the agent reports them. Cost uses a versioned price table configured per project.

Trigger

The user opens the usage dashboard or filters it.

Postconditions

  • On success: Aggregates show values, coverage (share of spans that reported the metric), and the price-table version used.
  • On failure: Unavailable aggregates are labeled; no partial total is presented as complete.

Main flow

  1. The system aggregates tokens, cost, and latency percentiles from the span store by project, agent version, model, tool, and time window.
  2. The user compares versions and opens contributing traces.
  3. Behavioral finding rates for the same filter appear beside usage, so a cheaper version that violates more policies is visible as such.

Alternative flows and exceptions

UC-16-A1 — Cancellation or interruption

The user may leave the dashboard at any time; nothing changes.

UC-16-E1 — Exceptions and recovery

Branch: Steps 1–3 of the main flow, as applicable.

Unreported token or cost values stay null and lower the coverage figure; they are never summed as zero. A model missing from the price table yields unknown cost for its spans.

Disposition: Show coverage and unknowns explicitly.

Acceptance criteria — AC-16

Totals state their coverage; null usage is never displayed as zero; every cost figure names its price-table version; dashboards respect project boundaries.

Notes

Shared rules: BR-03, BR-06. Query latency targets are open (NFR-11).

10.3 Release acceptance for the first complete slice

  1. RA-01. A customer-support agent exports OTLP spans following the pinned AgentProof profile, containing the reference tools find_customer, find_order, lookup_policy, request_approval, refund_order, and send_email where applicable.
  2. RA-02. Ingestion accepts and normalizes traces idempotently. It marks a trace complete only on the completion signal, and recovers accepted work after a worker or queue interruption.
  3. RA-03. The five initial failure classes WRONG_TOOL, INVALID_ARGUMENT, ACTION_LOOP, RETRIEVAL_LOOP, and POLICY_VIOLATION have controlled positive and negative scenarios.
  4. RA-04. Every confirmed finding leads to validated, project-authorized evidence and the exact policy or tool-specification version.
  5. RA-05. The Trace Explorer shows a successful outcome with a failed behavioral result for the high-value refund case.
  6. RA-06. Two agent versions can be evaluated on the same pinned dataset; comparison exposes missing data and incompatible inputs.
  7. RA-07. A mandatory regression gate returns FAIL for the policy regression, while incomplete or unavailable required analysis returns ERROR. The CI client exits with a distinct code for each result.
  8. RA-08. A reviewer can annotate findings without mutating canonical trace or machine-generated evidence.
  9. RA-09. The complete demonstration is exercised through the local deployment with backend integration and browser end-to-end tests.
  10. RA-10. With k > 1 trials, a case that violates the policy in only one trial still fails the mandatory gate, and the comparison lists it as flaky rather than as a clean pass.
  11. RA-11. The labeled scenario suite reports per-class precision, recall, and the INCONCLUSIVE rate; deterministic detectors have no errors on it (NFR-10).

These are planned acceptance checks. This document records no executed product tests or release approval.

ProjectAuthorization boundary for agents, traces, knowledge, policies, and evaluations.

BaselinePinned comparison run or approved agent version evaluated under compatible conditions.

Outcome / behavioral resultOutcome states whether the task completed; behavior states whether observed actions satisfy configured requirements. Neither substitutes for the other.
Span / trajectoryA span records one operation. A trajectory is the ordered, related sequence of actions in an agent run.
COMPLETE / PARTIAL / OPENTrace completeness states: complete under the declared contract, known to be incomplete, or still open for completion. They are separate from processing status.
Processing stateAccepted, queued, analyzing, completed, partial, or error visibility for asynchronous work; it does not by itself describe agent behavior.
INCONCLUSIVEAn affected check lacks enough evidence or decidable applicability to establish its result. Required incomplete checks cannot imply a passing gate.
PASS / FAIL / ERROR / pendingPASS: all gate rules verifiably satisfied. FAIL: a trustworthy complete evaluation breaches a rule. ERROR: no trustworthy decision can be produced. Pending: work is nonterminal.
CONFIRMED / DISMISSED / NEEDS_REVIEWHuman review states attached as annotations. They do not overwrite machine findings or automatically change gate eligibility.
CI / M2M / OIDC / PKCEContinuous integration; machine-to-machine authentication; OpenID Connect; Proof Key for Code Exchange for human sign-in.

Semantic critic / RCAA focused model-assisted evaluator; root-cause analysis explaining validated findings while labeling uncertainty and hypotheses.

Projection / idempotency / outboxA rebuildable derived view (in version 0.2, pgvector embeddings); safe repetition without duplicate effects; a durable job-publication record used to recover delivery.
Trial / pass^kOne execution of a case; a case runs k trials. pass^k is the probability that all k trials of a case succeed, as used by τ-bench to measure consistency.
