3. Overview

An AI agent can complete a task while skipping approval, choosing the wrong tool, repeating retrievals, or relying on unsupported evidence. Evaluating only the final answer can miss these execution failures.

AgentProof collects execution traces, checks tool use and policies, compares actual actions with expected workflows, and links confirmed findings to inspectable evidence. Developers investigate individual runs; reviewers assess findings; evaluation engineers and CI systems compare versions before a release.

Outcome success and behavioral correctness remain separate. The initial reference domain is customer support: a successful refund can still violate an approval requirement. Other domains need their own tool specifications, policies, and evaluation data.

Positioning statementFor teams releasing AI agents, AgentProof is a behavioral evaluation system that connects execution failures to validated evidence and release decisions. It extends final-answer evaluation with trace-level policy, workflow, and tool-use checks.

UC-01 — Enter a project and authorize access

Status: DraftPriority: Must within stated scopeScope: FoundationRequirements: FR-01, NFR-04, NFR-07, NFR-09

Description

Give a person or machine only the project resources and operations it is entitled to use.

Actors

Human user, CI client, collector. Supporting actor: Project administrator.

Preconditions

A project exists; the identity is registered and mapped to that project. A human can complete OIDC sign-in; a machine can obtain a client-credentials token.

Trigger

An actor requests a protected API operation.

Postconditions

  • On success: No cross-project resource data is disclosed; an authorized operation may proceed.
  • On failure: The protected operation is denied; no cross-project data is disclosed.

Main flow

  1. Auth0 issues an access token for the intended API audience with appropriate scopes.
  2. Traefik Hub validates token and coarse route or scope requirements.
  3. FastAPI resolves the actor and project context and checks operation-specific authorization.
  4. For resource access, FastAPI verifies the resource belongs to the project and the actor is allowed to access that project.
  5. The system performs the operation and records an audit event where required.

Alternative flows and exceptions

UC-01-A1 — Cancellation or interruption

Before token issuance or submission of the protected request, the actor may abandon the flow. No requested operation occurs. Abandoning a client does not undo an operation already authorized and performed.

UC-01-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

An expired or invalid token is rejected. A valid token with insufficient scope or incorrect project membership is denied. A request for a trace in another project is denied even if the token includes traces:read. Missing identity infrastructure prevents protected access; cached authorization must not silently grant new permissions.

Disposition: Reject invalid or expired tokens and deny insufficient scope or project access. Missing identity infrastructure ends protected access without granting new permissions.

Acceptance criteria — AC-01

Human and machine identities have distinct flows; project ownership is checked at the application boundary; M2M clients can be scoped to ingestion or evaluation without projects:admin; denials are auditable without leaking sensitive resource contents.

Shared rules: BR-03, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-02 — Register an agent and versioned evaluation context

Status: DraftPriority: Must within stated scopeScope: FoundationRequirements: FR-02, NFR-04, NFR-06

Description

Define the agent, tools, policies, and expected workflows needed to interpret its runs.

Actors

Project administrator and policy owner.

Preconditions

The actors have project administration or policy-writing permissions.

Trigger

The team onboards an agent or publishes a change to its behavior contract.

Postconditions

  • On success: New evaluations can pin exact agent, policy, workflow, and tool-specification versions; historical runs keep their original versions.
  • On failure: Invalid context is not published. Existing versions remain unchanged; projection failures remain visible.

Main flow

  1. The administrator creates an agent identity and registers an agent version, including code or prompt revision metadata where available.
  2. The policy owner publishes versioned policy clauses and identifies the side effects and sensitivity of each tool.
  3. The owner defines required, optional, conditional, and forbidden workflow transitions.
  4. The system validates references between policies, tools, and workflow steps; it records immutable versions in PostgreSQL.
  5. Background jobs update scoped Qdrant indexes and Neo4j relationship projections; the source version remains available to evaluations independently of index state.

Alternative flows and exceptions

UC-02-A1 — Cancellation or interruption

Before publication at step 4, the actor may abandon changes without creating a published version. A published artifact remains immutable; a correction requires a new version.

UC-02-E1 — Exceptions and recovery

Branch: Steps 4–5 of the main flow, as applicable.

An invalid tool reference or contradictory workflow is rejected with a specific validation error. Replacing a published rule produces a new version. A failed index update leaves the authoritative version intact but marks retrieval or graph-dependent analysis unavailable until rebuilt.

Disposition: Validation errors return to steps 2–3 for correction. Publishing a replacement creates a new version. A failed projection update leaves the authoritative version intact and dependent analysis unavailable until recovery.

Acceptance criteria — AC-02

A past finding resolves its original policy clause after a policy update; a semantic search applies project and version filters; changing an artifact does not silently rewrite prior decisions.

Notes

Shared rules: BR-03, BR-04. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-03 — Ingest and normalize an agent trace

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-03, NFR-01, NFR-04, NFR-05, NFR-07

Description

Turn an agent's telemetry into a project-scoped canonical execution record without performing expensive analysis in the request path.

Actors

Customer agent or OTel Collector.

Preconditions

The caller has a scoped ingestion identity and an existing project and agent version. A redaction configuration is active.

Trigger

The caller submits OTLP-compatible spans or a supported framework-specific trace.

Postconditions

  • On success: An accepted trace is retrievable with a visible processing state and durable path to analysis.
  • On failure: Rejected input is not acknowledged as accepted. Persisted work remains recoverable and is not reported as analyzed.

Main flow

  1. The gateway and ingestion entrypoint authenticate the caller, enforce project boundaries and payload limits, and validate trace identifiers and structure.
  2. Redaction runs before sensitive fields are persisted. The adapter maps source spans to canonical agent, LLM, tool, retrieval, handoff, guardrail, and approval types.
  3. The normalizer reconstructs parent-child and chronological relationships, records warnings, and marks the trace COMPLETE, PARTIAL, or OPEN according to an explicit completion contract.
  4. PostgreSQL stores the canonical trace, source metadata needed for diagnostics, and a durable analysis-job record using a stable idempotency key.
  5. The ingestion API acknowledges acceptance. Job publication to Redis is retried or recovered by an outbox/sweep if the queue is temporarily unavailable.

Alternative flows and exceptions

UC-03-A1 — Cancellation or interruption

Before submission, the sender may abandon the upload. After durable acceptance, disconnecting does not cancel analysis; a retry uses the same idempotency key.

UC-03-E1 — Exceptions and recovery

Branch: Steps 1–5 of the main flow, as applicable.

Duplicate delivery returns the existing trace or an idempotent acknowledgement without duplicate findings. Malformed payloads are rejected with actionable errors. A missing parent span is recorded as incomplete structure. A database failure prevents successful acceptance. A persisted but temporarily unqueued trace remains recoverable and is never reported as fully analyzed.

Disposition: Reject invalid payloads or unsuccessful persistence without acceptance. Duplicate submissions return the existing result. Incomplete structure remains explicit; accepted but unqueued work stays recoverable and pending analysis.

Acceptance criteria — AC-03

Replaying the same delivery does not multiply traces; a worker crash or queue outage cannot silently lose accepted work; redacted values are absent from normal persisted views; trace completeness is available to downstream detectors.

Notes

Shared rules: BR-02, BR-03, BR-06, BR-07. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-04 — Inspect a trace and its execution trajectory

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-04, NFR-03, NFR-04, NFR-06, NFR-07

Description

Let a developer understand what happened and reach the evidence for any finding.

Actors

Agent developer.

Preconditions

A trace exists in the developer's authorized project.

Trigger

The developer selects a trace from the project view.

Postconditions

  • On success: The user can reconstruct the reported behavior from source records and identify any unavailable analysis components.
  • On failure: Unavailable views are labeled; access failure does not expose protected data or imply successful analysis.

Main flow

  1. The UI shows outcome, behavioral and analysis states separately, plus the agent and policy versions.
  2. The developer switches between chronological and hierarchical spans and filters tool, LLM, retrieval, handoff, and approval events.
  3. The UI displays redacted arguments, statuses, timing, token use, and available costs.
  4. The developer selects a finding, follows its evidence IDs to the relevant spans and policy or workflow version, and opens the expected-versus-actual path view.

Alternative flows and exceptions

UC-04-A1 — Cancellation or interruption

The developer may close the view at any step. No trace or analysis record changes.

UC-04-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A partial trace is marked clearly; an incomplete run must not imply that an unseen approval was absent. If the graph projection is unavailable, the canonical span timeline and findings can still be displayed, with the graph view marked unavailable. Raw payload access requires additional authorization and audit logging.

Disposition: Continue with completeness warnings or the canonical timeline when the graph is unavailable. Deny unauthorized raw reads; the user may continue using the redacted view.

Acceptance criteria — AC-04

Each visible confirmed finding links to resolvable evidence in the same authorized project; the UI preserves ordering and parent-child distinctions; sensitive values remain masked in standard views.

UC-05 — Detect tool misuse and invalid arguments

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-05, NFR-02, NFR-04, NFR-05, NFR-06

Description

Identify a wrong tool choice or an invalid invocation using the strongest available evidence.

Actors

Analysis worker. Beneficiary: Agent developer.

Preconditions

Tool specifications and relevant domain state are versioned; the trace includes the required tool call data.

Trigger

UC-03 queues a trace for analysis.

Postconditions

  • On success: The run has validated findings, unconfirmed candidates, or an explicit insufficient-evidence state.
  • On failure: Insufficient evidence remains inconclusive; an unsupported claim is not confirmed.

Main flow

  1. The worker checks tool names, schema versions, argument types, permitted ranges, and domain constraints using deterministic validators.
  2. It distinguishes a schema violation from an argument that is structurally valid but inconsistent with observed state, such as refunding more than the order value.
  3. If tool choice requires interpreting the task intent, a candidate WRONG_TOOL finding is passed to a bounded semantic critic with the task, tool specifications, and relevant spans.
  4. The evidence validator resolves cited records and verifies values before a finding is confirmed.

Alternative flows and exceptions

UC-05-A1 — Cancellation or interruption

This is an automated check, with no interactive cancel operation specified. Worker interruption leaves work retryable and incomplete rather than passed.

UC-05-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A missing specification or hidden required argument makes the assessment INCONCLUSIVE; it is not a clean pass. A failed tool call can still have invalid arguments, but execution failure and misuse are separate observations. If a side-effecting tool was already executed, AgentProof reports the event and its risk; the initial product does not retroactively prevent execution.

Disposition: Missing required specifications or argument evidence ends the affected check as INCONCLUSIVE. Execution failure is recorded separately; already executed side effects remain observed events.

Acceptance criteria — AC-05

INVALID_ARGUMENT and WRONG_TOOL are distinct; findings cite the tool span and specification or domain value; the report identifies whether validation preceded or followed the action.

Notes

Shared rules: BR-01, BR-04, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-06 — Verify policies and expected trajectories

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-06, NFR-02, NFR-04, NFR-05, NFR-06

Description

Determine whether observed actions satisfy applicable business rules and workflow prerequisites.

Actors

Policy owner and analysis worker.

Preconditions

The run is associated with an immutable policy/workflow version and enough trace data to decide the relevant constraints.

Trigger

A trace contains a governed action or an evaluation requests workflow conformance.

Postconditions

  • On success: Applicable checks and path differences are recorded with source versions and evidence.
  • On failure: Uncertain applicability or completeness remains explicit; invalid configuration cannot create a trustworthy pass.

Main flow

  1. The worker identifies applicable policy conditions from tool arguments and prior observed state.
  2. It evaluates deterministic requirements first: required steps, order, conditional branches, forbidden transitions, and approval before side effects.
  3. The trajectory comparer emits a machine-readable difference: missing, unexpected, repeated, wrong-order, forbidden, or incomplete step.
  4. For ambiguous natural-language clauses, semantic retrieval obtains the exact policy version and a policy critic proposes a judgment.
  5. The validator checks the source clause, relevant spans, event order, and trace completeness before confirming a POLICY_VIOLATION or related finding.

Reference scenario

For refund_order(order_id=1024, amount=800), policy REFUND-004 version 3 requires policy lookup and human approval before the refund. If a complete trace shows find_order → refund_order, the system reports the missing prerequisites while preserving Outcome: SUCCESS if the refund actually completed.

Alternative flows and exceptions

UC-06-A1 — Cancellation or interruption

This is an automated check, with no interactive cancel operation specified. Interrupted checks remain incomplete and cannot establish conformance.

UC-06-E1 — Exceptions and recovery

Branch: Steps 1–5 of the main flow, as applicable.

An optional branch does not fail merely because it was skipped. If policy applicability is undecidable or the trace is partial at the approval boundary, return INCONCLUSIVE or an analysis error according to the evaluation contract; do not assert absence from incomplete evidence. Contradictory policies are reported as a configuration error.

Disposition: Skip inapplicable optional branches. Undecidable applicability or incomplete intervals produce INCONCLUSIVE or an analysis error. Contradictory policies stop the affected check as a configuration error.

Acceptance criteria — AC-06

Same inputs and rule versions produce the same deterministic result; missing and wrong-order steps are distinguished; a confirmed violation names the exact clause and ordered action spans; partial traces cannot create a false missing-approval claim.

Notes

Shared rules: BR-01, BR-02, BR-04, BR-05, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-07 — Detect loops and inefficient behavior

Status: DraftPriority: Must within stated scopeScope: MVP, with later semantic expansionRequirements: FR-07, NFR-02, NFR-04, NFR-05, NFR-06

Description

Find repeated or unnecessary work and quantify its observed cost where the data permits.

Actors

Analysis worker.

Preconditions

The trace contains ordered actions; retrieval-result hashes or summaries and usage metrics are available for semantic or cost analysis.

Trigger

The worker analyzes an accepted trace or an evaluation aggregates runs.

Postconditions

  • On success: Findings such as ACTION_LOOP, RETRIEVAL_LOOP, NO_PROGRESS, or INEFFICIENT_TRAJECTORY carry relevant span sequences and method/configuration versions.
  • On failure: Unavailable evidence limits the assessment; missing usage does not become a zero-cost result.

Main flow

  1. Deterministic checks detect repeated identical calls and repeated subsequences.
  2. Retrieval analysis measures overlap or semantic similarity between consecutive results and checks for new evidence or state changes.
  3. The worker excludes retries that a tool policy explicitly permits and labels uncertain efficiency judgments as candidates.
  4. It reports observed extra calls, tokens, and latency; avoidable cost is an estimate only when its counterfactual assumptions are stated.

Alternative flows and exceptions

UC-07-A1 — Cancellation or interruption

This is an automated check, with no interactive cancel operation specified. Interruption leaves unfinished assessment visible; observed metrics are not fabricated.

UC-07-E1 — Exceptions and recovery

Branch: Steps 2–4 of the main flow, as applicable.

Similar queries can be justified if results or task state change materially. Missing retrieval outputs prevent a confident RETRIEVAL_LOOP decision. A Qdrant outage does not erase deterministic repetition findings but can make semantic progress assessment unavailable.

Disposition: Changed results or state and permitted retries may justify repetition. Missing outputs or semantic-search outages leave affected progress assessments unavailable; deterministic findings remain available.

Acceptance criteria — AC-07

Exact loops need no LLM; permitted retries do not trigger false positives; a semantic-loop finding includes the compared evidence or summaries and configured decision threshold; estimated impact is labeled separately from observed usage.

Notes

Shared rules: BR-01, BR-04, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-08 — Validate semantic judgments and generate an RCA

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-08, NFR-04, NFR-05, NFR-06, NFR-07

Description

Explain confirmed failures without promoting unsupported model claims to facts.

Actors

Analysis worker. Beneficiary: Reviewer.

Preconditions

Candidate findings exist; retrievable evidence has project, version, and access metadata.

Trigger

Deterministic or statistical analysis submits a candidate requiring contextual judgment or explanation.

Postconditions

  • On success: The report has traceable assertions, or it clearly states that a causal claim cannot be established.
  • On failure: Unsupported causal claims remain unconfirmed, with validation diagnostics and available deterministic findings retained.

Main flow

  1. A retriever builds a bounded evidence package from authorized Qdrant candidates, Neo4j relationships, and authoritative PostgreSQL records.
  2. LangGraph routes the package to applicable trajectory, policy, or efficiency critics; each returns a structured decision, reason, uncertainty, and evidence IDs.
  3. The evidence validator checks IDs, source versions, quoted values, graph relationships, metric calculations, and redaction constraints.
  4. A valid judgment can become a confirmed finding. Unsupported claims remain unconfirmed and are visible as insufficient evidence or analysis diagnostics.
  5. The RCA synthesizer combines validated findings with relevant relationships and clearly separates observed facts, rule-derived conclusions, semantic judgments, and hypotheses. Recommendations point to a concrete action or control.

Alternative flows and exceptions

UC-08-A1 — Cancellation or interruption

No interactive cancellation is specified for critic jobs. Interrupted judgment or synthesis remains incomplete; prior validated findings remain available.

UC-08-E1 — Exceptions and recovery

Branch: Steps 1–5 of the main flow, as applicable.

An LLM response without evidence IDs cannot confirm a finding. A source record missing from a projection is verified against the authoritative store; unrecoverable discrepancies become analysis errors. Prompt-injection text in retrieved material is treated as data, not as an instruction to the critic. An unavailable LLM does not invalidate already confirmed deterministic findings.

Disposition: Unverifiable claims remain unconfirmed. Check missing projection evidence against the source; unrecoverable discrepancies become analysis errors. LLM outages preserve confirmed deterministic findings.

Acceptance criteria — AC-08

Every confirmed semantic finding has validated evidence IDs; an RCA cannot claim that a planner failed to read a policy as an observed fact unless the trace supports it; validators record rejection reasons; models do not have unrestricted datastore access.

Notes

Shared rules: BR-01, BR-03, BR-04, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-09 — Review a finding and its evidence

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-09, NFR-04, NFR-06, NFR-09

Description

Allow a human to confirm, dismiss, or request follow-up on an analysis result.

Actors

Reviewer.

Preconditions

A finding or candidate exists in an authorized project.

Trigger

The reviewer opens a finding from the trace or evaluation UI.

Postconditions

  • On success: The original result and human judgment remain independently inspectable.
  • On failure: No unauthorized or conflicting annotation replaces the original result or a prior review.

Main flow

  1. The reviewer sees the failure type, severity, evaluator version, confidence if applicable, evidence, source policy, trace completeness, and system analysis state.
  2. The reviewer follows evidence references and records CONFIRMED, DISMISSED, or NEEDS_REVIEW, with an optional rationale.
  3. The system stores a separate, timestamped annotation with actor identity and preserves the machine-produced finding and evidence.
  4. Evaluation reports distinguish automated findings from reviewer decisions; if review changes gate eligibility, the gate is recomputed with the review-policy version recorded.

Alternative flows and exceptions

UC-09-A1 — Cancellation or interruption

Before submitting step 2, the reviewer may leave without adding an annotation. A committed annotation remains auditable and does not disappear when the view closes.

UC-09-E1 — Exceptions and recovery

Branch: Steps 1–3 of the main flow, as applicable.

An unauthorized reviewer cannot see or annotate a finding. An annotation submitted against an obsolete version prompts a conflict resolution rather than silently replacing another review.

Disposition: Deny unauthorized review access. An obsolete annotation version requires conflict resolution and resubmission at step 2; the existing review is not silently overwritten.

Acceptance criteria — AC-09

Review actions are auditable; dismissing one finding does not delete its trace or evidence; exported evaluation data includes the review state and policy governing its effect on gates.

Notes

Shared rules: BR-01, BR-03, BR-08. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-10 — Evaluate an agent version on an external test run

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-10, NFR-04, NFR-05, NFR-06, NFR-08

Description

Produce an evaluation run from customer-executed agent cases without running arbitrary customer code inside AgentProof.

Actors

Evaluation engineer and CI system.

Preconditions

A versioned dataset and evaluation configuration exist; the client can authenticate and execute its own agent.

Trigger

A developer proposes a code, prompt, tool, model, or workflow change.

Postconditions

  • On success: The run is completed with reproducible inputs or has an explicit error and diagnostic record.
  • On failure: Incomplete or failed required work is visible; no apparently complete successful report is published.

Main flow

  1. The client creates an evaluation run pinned to project, agent candidate version, dataset version, policy/workflow versions, and evaluator configuration.
  2. Customer CI executes each case and submits resulting traces with case IDs and idempotency keys.
  3. The client signals that submission is complete. The system freezes the expected case set and waits for ingestion and all required analysis jobs to reach terminal states.
  4. The evaluator aggregates outcomes, finding rates, policy violations, trajectory conformance, latency, tokens, and cost, preserving denominators and missing-data counts.
  5. The system publishes a versioned report and exposes a machine-readable result when the run is complete.

Alternative flows and exceptions

UC-10-A1 — Cancellation or interruption

Before creating the run, the client may abandon the request. After creation, stopping uploads leaves an incomplete run; a configured deadline may yield ERROR. No evaluation-cancel API is specified.

UC-10-E1 — Exceptions and recovery

Branch: Steps 2–5 of the main flow, as applicable.

Missing cases, duplicate IDs, incomplete traces, or required critic failures prevent an apparently complete evaluation. A deadline can mark the run ERROR with the missing work recorded; it does not imply that the candidate passed. Retrying a trace upload or finalize request is idempotent. A case outcome that the customer did not provide is not inferred from a polished final answer.

Disposition: Submission completion does not mean evaluation completion. Missing cases, conflicting IDs, incomplete traces, or failed required critics keep the run incomplete or yield ERROR at its deadline. Safe retries reuse the existing submission or finalize result.

Acceptance criteria — AC-10

The system never executes the customer's production agent; an evaluation cannot be finalized while required analyses are pending; each metric exposes numerator, denominator, exclusions, and configuration version.

Notes

Shared rules: BR-04, BR-05, BR-06, BR-07. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-11 — Compare a candidate with a baseline

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-11, NFR-04, NFR-06, NFR-08

Description

Determine whether a proposed agent version regresses in behavior, quality, latency, or cost.

Actors

Evaluation engineer.

Preconditions

Candidate and baseline evaluations are complete and have compatible dataset, policy, metric definitions, and evaluator settings; differences are explicitly documented where comparison is allowed.

Trigger

The engineer selects a candidate and an approved baseline, or UC-12 requests comparison.

Postconditions

  • On success: A reproducible comparison links each aggregate to source evaluation runs and contributing cases.
  • On failure: An incompatible comparison yields an error, not a misleading regression percentage.

Main flow

  1. The system validates compatibility and records the comparison inputs.
  2. It presents side-by-side outcome and trajectory metrics, absolute changes, relative changes where the denominator is nonzero, and uncertainty or sample-size context where appropriate.
  3. The engineer drills into cases contributing to a changed metric and opens their trace-level findings.
  4. The comparison becomes a pinned input to a gate decision.

Alternative flows and exceptions

UC-11-A1 — Cancellation or interruption

The engineer may leave the comparison view at any time. Candidate and baseline evaluations remain unchanged; no gate promotion follows from leaving.

UC-11-E1 — Exceptions and recovery

Branch: Steps 1–2 of the main flow, as applicable.

Incompatible or missing dataset versions produce a comparison error rather than a misleading percentage. A baseline metric of zero requires a defined handling rule instead of division by zero. Missing token or cost data remains visible as missing data, not a zero-valued improvement.

Disposition: Incompatible or missing dataset versions end the comparison with an error. A zero baseline uses an explicitly defined rule; missing cost or token data remains missing rather than an improvement.

Acceptance criteria — AC-11

Critical policy failures are not hidden inside a composite score; absolute and relative deltas are distinct; a comparison can be traced to its exact baseline and candidate versions.

Notes

Shared rules: BR-04, BR-05, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-12 — Enforce a CI regression gate

Status: DraftPriority: Must within stated scopeScope: MVPRequirements: FR-12, NFR-04, NFR-06, NFR-08, NFR-09

Description

Provide a reliable decision for an existing CI system before an agent version is promoted.

Actors

CI system. Supporting actor: Evaluation engineer.

Preconditions

A versioned gate definition exists; the candidate and baseline meet UC-10 and UC-11 requirements. CI has narrowly scoped M2M permissions.

Trigger

The CI workflow requests a gate result for the completed evaluation.

Postconditions

  • On success: The decision and its exact gate, input, metric, and evaluator versions are stored and inspectable.
  • On failure: ERROR and pending never permit automatic promotion; the decision includes diagnostics.

Main flow

  1. The system evaluates each configured requirement against pinned metrics, findings, and baseline changes.
  2. Mandatory safety requirements are evaluated independently of improvements in unrelated measures.
  3. It returns PASS if all requirements are verifiably satisfied, or FAIL with each breached requirement and its observed value if the complete trustworthy evaluation violates at least one requirement.
  4. CI continues promotion only for PASS; it presents the report and stops promotion for FAIL.

Alternative flows and exceptions

UC-12-A1 — Cancellation or interruption

If CI stops waiting or times out, promotion remains blocked. Abandoning the request cannot convert a pending or erroneous result to PASS.

UC-12-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A pending evaluation returns a nonterminal state. Unavailable required analyses, missing cases, stale projections needed for a requirement, incompatible baseline, or internal failure produce ERROR and diagnostics. CI must block automatic promotion for ERROR as well as FAIL; a manual override, if ever supported, is a separate authorized and audited process.

Disposition: Pending work returns a nonterminal response; missing or untrustworthy required inputs return ERROR. CI blocks promotion for both. A future manual override would require separate authorization and audit.

Acceptance criteria — AC-12

Gate outcomes are stable for the same pinned inputs; CI distinguishes PASS, FAIL, ERROR, and pending; policy-violation limits cannot be offset by improved task success; a response includes a concise machine-readable explanation.

Notes

Shared rules: BR-04, BR-05, BR-06, BR-08. Unresolved configuration and ownership decisions are tracked in section 7.3.

UC-13 — Govern sensitive trace data and derived projections

Status: DraftPriority: Must within stated scopeScope: MVP controls; operations mature laterRequirements: FR-13, NFR-04, NFR-05, NFR-07, NFR-09

Description

Keep telemetry accessible only to authorized people and honor data retention or deletion policy across all derived stores.

Actors

Project administrator. Supporting actor: Operations worker.

Preconditions

Data is associated with a project and has a declared classification, retention policy, and redaction settings.

Trigger

A privileged read, scheduled retention expiry, or authorized deletion request occurs.

Postconditions

  • On success: The system reaches a verifiable deletion state, or explicitly exposes incomplete propagation for follow-up.
  • On failure: Incomplete deletion propagation remains pending and visible; erased source content cannot be restored by a rebuild.

Main flow

  1. The system enforces project and role checks before disclosing trace fields and records privileged raw-payload access.
  2. At expiry or authorized erasure, PostgreSQL marks the source records and manages deletion according to the chosen policy.
  3. A durable deletion/reprojection job removes or invalidates corresponding Qdrant vectors, Neo4j nodes/edges, and any relevant caches.
  4. The system verifies the projection state and keeps an audit record that does not itself re-expose erased content.

Alternative flows and exceptions

UC-13-A1 — Cancellation or interruption

Before an authorized deletion request is submitted, the administrator may abandon it. Once deletion starts, closing the interface does not reverse erasure or cancel propagation.

UC-13-E1 — Exceptions and recovery

Branch: Steps 1–4 of the main flow, as applicable.

A projection outage leaves the request pending with a retryable status and blocks reindexing of deleted source material. A legal or operational hold, if implemented, must be a separately authorized and documented rule. A request for data outside the administrator's project is denied.

Disposition: Deny cross-project requests. A projection outage leaves deletion pending and retryable while preventing deleted-source reindexing. Any hold requires a separately authorized, documented policy.

Acceptance criteria — AC-13

Erased data does not reappear after index rebuilds; access to raw payloads is recorded; error paths do not leak sensitive fields; each project can identify its configured retention and redaction policy.

Notes

Shared rules: BR-03, BR-06. Unresolved configuration and ownership decisions are tracked in section 7.3.

Policy: REFUND-004 version 3 requires a policy lookup and human approval before a refund above $500.

2Customer CI runs case refund-1024 with requested amount $800Trace with case ID and agent version
3Agent calls find_order(1024) then refund_order(1024, 800)Complete trace; no approval span in the relevant interval

10.3 Release acceptance for the first complete slice

  1. RA-01. A customer-support agent exports a trace containing the reference tools find_customer, find_order, lookup_policy, request_approval, refund_order, and send_email where applicable.
  2. RA-02. Ingestion accepts and normalizes traces idempotently, records completeness, and recovers accepted work after a worker or queue interruption.
  3. RA-03. The five initial failure classes WRONG_TOOL, INVALID_ARGUMENT, ACTION_LOOP, RETRIEVAL_LOOP, and POLICY_VIOLATION have controlled positive and negative scenarios.
  4. RA-04. Every confirmed finding leads to validated, project-authorized evidence and the exact policy or tool-specification version.
  5. RA-05. The Trace Explorer shows a successful outcome with a failed behavioral result for the high-value refund case.
  6. RA-06. Two agent versions can be evaluated on the same pinned dataset; comparison exposes missing data and incompatible inputs.
  7. RA-07. A mandatory regression gate returns FAIL for the policy regression, while incomplete or unavailable required analysis returns ERROR.
  8. RA-08. A reviewer can annotate findings without mutating canonical trace or machine-generated evidence.
  9. RA-09. The complete demonstration is exercised through the local deployment with backend integration and browser end-to-end tests.

These are planned acceptance checks. This document records no executed product tests or release approval.

Candidate findingSuspected failure awaiting sufficient evidence or validation.
